# Architecture decisions

Record significant, enduring choices and their reasons here. An ADR explains a
decision; current architecture documentation explains how the system works.
Use an ADR for consequential boundaries, interfaces, constraints or tradeoffs that
future maintainers might otherwise unknowingly reverse. Routine edits do not need one.

Use sequential filenames such as `0001-descriptive-choice.md` and the adjacent
`template.md`. Record status, context, decision, alternatives/consequences and
supporting evidence. States are Proposed, Accepted, Superseded and Deprecated.
Link successors when superseding a decision; preserve historical context.

For retrospective records, distinguish current evidence from unknown historical
rationale. Never invent an original date or owner approval. Recording an existing
decision does not authorize a new implementation. Resolve consequential conflicts
with the owner under the lifecycle's existing authority rules.
