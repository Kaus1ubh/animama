# Internationalization

The interface renders in the owner's UI Locale: English (`en`) or the beta
`ja`, `ko`, `zh-Hans` and `zh-Hant`. The UI Locale only changes interface text
and formatting. It never changes what an Anima says or hears, and it is not the
crisis-resource region
([ADR 0024](../../adr/0024-ui-locale-separate-from-conversation-language.md)).

## Where it lives

| Piece | Location |
| --- | --- |
| Supported locales, matching, resolution, formatting region | `packages/runtime-contracts/src/locale.ts` (`@animama/runtime-contracts/locale`) |
| i18next instance, provider, formatters, pseudo-locale | `packages/product-ui/src/i18n/` (`@animama/product-ui/i18n`) |
| Shared product UI strings (`product` namespace) | `packages/product-ui/src/locales/<tag>/product.json` |
| Web application strings | `web/src/locales/<tag>/<namespace>.json` |
| Web wiring | `web/src/i18n/` (catalog loading, first-paint locale, `LocaleSync`) |
| Desktop shell strings (startup page, window titles, application menu) | `desktop/src/locales/<tag>.json` |
| macOS microphone prompt translations | `desktop/build/locales/<lproj>.lproj/InfoPlist.strings` |
| Product term list for translations | `src/frontend/i18n/terms.json` |
| Saved preference | App settings `locale` (`GET/PATCH /v1/users/me/settings`), `null` = System default |

English catalogs are bundled and are the fallback for every missing key.
Other locales are separate chunks loaded only when active, so the desktop app
needs no network access for them.

## Choosing the locale

Both entrypoints create the i18next instance before the first render with the
locale this browser last applied, or else the first supported language in
`navigator.languages`, or else English. `LocaleSync` then applies the saved App
setting once it loads, and re-resolves "System default" when the browser fires
`languagechange`. Switching calls `i18n.changeLanguage`: screens stay mounted
and keep their state, and `<html lang>`/`dir` follow.

The picker is the Language row in App Settings → Appearance. It lists each
locale in its own script (so a user who cannot read the active locale can still
find English) and marks beta locales.

## Desktop shell

The Electron shell words its own surfaces: the startup and recovery page, the
PiP and Quick Chat window titles, and the application menu. It cannot read App
settings while the backend is down, so it keeps small catalogs in
`desktop/src/locales/<tag>.json` and resolves its locale with the shared
resolver: the locale the app last applied on this machine, else the first
supported language in `app.getPreferredSystemLanguages()`, else English. A key
missing from a beta catalog shows its English text.

`LocaleSync` in the main window reports each applied locale through
`window.animamaDesktop.locale.setApplied(tag)` (IPC `animama:locale:set`).
Main accepts it only from the registered main window and only as a canonical
tag, so PiP, Quick Chat, the recovery page and the pseudo-locale never change
it. It caches the tag in `ui-locale.json` (`{version: 1, locale}`) in the
profile directory; a missing or invalid file falls back to the OS languages
and is replaced by the next report. A change rebuilds the menu, retitles open
PiP and Quick Chat windows and reloads the hidden recovery page.

The menu is Electron's default menu written out with catalog labels; its roles,
accelerators and native macOS actions are unchanged. Items macOS adds itself
(Services entries, Start Dictation, Emoji & Symbols, window tiling) follow the
macOS language, as does the microphone permission prompt: macOS reads the
translated `NSMicrophoneUsageDescription` from `InfoPlist.strings` in the
`ja`, `ko`, `zh_CN` and `zh_TW` lproj folders Electron already ships (so the
bundle gains no localization), and English from `Info.plist`. The Windows
installer stays English.

## Adding or changing strings

1. Add the English text to the namespace's catalog in `web/src/locales/en/`
   (or `packages/product-ui/src/locales/en/product.json`). Keys are nested and named
   by meaning (`appearance.language.label`), not by English wording.
2. Use it through `useTranslation("<namespace>")` and `t("key")`; keys are typed
   from the English catalogs. Product UI code uses `useProductTranslation()`
   instead, which falls back to English for hosts without an Animama i18n
   provider; text built outside React stores catalog references and is worded
   at render (as chat failures do). Web code outside React uses
   `getI18n().getFixedT(null, "<namespace>")`; the extractor does not see
   `getI18n().t("<namespace>:key")`. Run `pnpm i18n:extract` (from `src/frontend`) to
   regenerate `web/src/i18n/resources.d.ts`.
3. Interpolate values (`{{name}}`) instead of concatenating, and use one key
   per sentence. Plurals use `_one`/`_other` suffixes with `count`; locales
   such as Japanese and Korean need only `_other`. `{{label, lowercase}}`
   lowercases an interpolated label where a language wants it, and
   `{{items, list}}` joins an array in the locale's style.
4. Write keys literally, or through a local union type or `switch`, so the
   extractor can see them. A key built from an imported type can be reported as
   unused and removed.
5. Translate the new key into every beta catalog with the term list: keep
   `Animama` and `Anima` in Latin script, use the listed renderings for product
   terms, and keep placeholders, plural suffixes and markup unchanged.

Settings sections and groups have stable IDs mapped to catalog labels. App
Settings search matches the translated title, description, group and section,
and also the English keywords.

Never translate stored data. Settings section IDs, persisted labels (for
example the `Base` and `Expression` beat labels) and content identifiers stay
as they are; map them to catalog keys for display. The backend sends codes and
parameters; the frontend words them.

The entry files (`main.local.tsx`, `main.hosted.tsx`) import the application's
modules only after `createWebI18n` resolves, so code that runs while a module
loads, such as a store's initial state, can translate in the first-paint
locale. Browser fixtures load the same way through
`tests/fixtures/with-i18n.ts`. Text worded while a module loads does not follow
a later locale switch, so prefer wording at render.

Format dates, times, numbers, lists and file sizes with `useFormatters()` from
`@animama/product-ui/i18n` rather than `toLocale*` or a hard-coded `en-US`.

## Safety text

The AI notice, crisis card and safety labels translate like other strings; the
crisis services, numbers and descriptions are verified backend data and stay as
sent. The safety and crisis protocol (`docs/safety/crisis-protocol.md`) has
machine translations beside it (`crisis-protocol.<locale>.md`) marked as such;
update every translation whenever the English changes. Prompt suggestions
translate their labels but send the English prompt, because the UI Locale never
chooses the conversation language.

## Backend failures

The backend sends stable codes (and `params` where wording needs values, such
as Loadout warnings); the `errors` namespace words them as
`errors:<area>.<code>`. Read a failure with `readApiError` and word it with
`apiErrorText(info, area)` from `web/src/lib/errors/apiError.ts`
(`creationErrors.ts` and `loadoutErrors.ts` wrap the creation and Loadout
cases). A code without wording shows the backend's English text in English and a
translated generic message elsewhere, with the English kept as secondary
detail. A worded code with several possible backend causes (such as
`anima_creation_defaults_unavailable`) keeps the backend text as detail in every
locale. English that carries no code, such as an error stored with a Memory
Manager run or an upload, follows the same rule through `uncodedErrorText`. An
error the frontend words itself extends `WordedError`, which `apiErrorText`
shows as it is in every locale.
Error keys are runtime values, so extraction preserves `errors:**`;
`web/src/lib/errors/userVisibleCodes.json` lists the codes that must be worded,
and its test requires each in every catalog. Add a code there when the UI can
show it.

## Checks

- `pnpm i18n:check` (part of `pnpm check` and `pnpm ci:source`) fails when:
  - English catalogs and the keys used in code differ (`i18next-cli extract --ci --dry-run`);
  - generated key types are stale;
  - application code contains raw JSX text, on any element or component, or
    user-visible attributes such as `label`, `description`, `aria-label` and
    `placeholder` (`i18next-cli lint`), or literal `toast()` text (ESLint);
  - a translated catalog (web, product UI or desktop shell) has a key English
    lacks or changes a placeholder.
- `pnpm i18n:status` lists untranslated keys per locale. They are reported, not
  failures, and render in English.
- `web/i18n-scope.json` lists the `exempt` developer and debug tools, which
  stay English; everything else under `web/src` except tests is linted. The lint
  cannot see English in plain code (thrown errors, constants), so word those
  with `getFixedT`, `WordedError` or `failureLine`.
- `pnpm e2e:test:pseudo` walks setup, chat, Library, two creators and App
  Settings under the pseudo-locale on a development stack and fails on visible
  unmarked text; see [Browser Journeys](../testing/browser-journeys.md#pseudo-locale-smoke).

Vitest runs with English catalogs (`web/src/test/i18n-setup.ts`), so tests may
assert English text. Browser journeys also run in English.

## Pseudo-locale

In development builds, open the app with `?ui-locale=pseudo` to render every
catalog string accented, lengthened and wrapped in `⟦ ⟧`. Plain text on screen
is an unconverted string; clipped text shows a layout that cannot absorb longer
translations. `?ui-locale=off` returns to the normal locale. The pseudo-locale
is never offered in the picker.

## Adding a locale

1. Add the tag, its native name and any matching rule in `locale.ts`, its case
   in product-ui's `loadProductCatalog`, and the tag to the backend `UiLocale`
   literal (`src/backend/animama/domain/settings.py`); regenerate the SDK with
   `pnpm openapi-ts` and bump the contract and package versions
   (`scripts/package-sets/README.md`).
2. Add the locale to `src/frontend/i18n/terms.json`, then create its catalogs.
3. Check its script renders with the system fonts (Devanagari and Vietnamese
   tone marks are not in the bundled DM Sans subsets) and review the main
   screens at desktop and narrow widths.
